# DeepScalper Experiment Management Recommendation

## Executive Summary
For the DeepScalper MLOps pipeline, we recommend a **Hybrid "Flight Log & Cockpit" Approach**.
*   **The "Flight Log" (Markdown)**: Use `randd_log.md` as the *Permanent Record* of verified findings. This leverages strict Git version control.
*   **The "Cockpit" (Jupyter Notebook)**: Use a new `notebooks/DeepScalper_Control_Plane.ipynb` as the *Operational Interface* to launch, monitor, and visualize runs interactively.

---

## 1. The Strategy: "Log vs. Lab"

| Components | **The "Flight Log" (Markdown)** | **The "Cockpit" (Notebook)** |
| :--- | :--- | :--- |
| **Role** | **Permanent Record** | **Interactive Lab** |
| **File** | `randd_log.md` / `experiments/inventory.md` | `notebooks/Control_Plane.ipynb` |
| **Use Case** | Audits, Post-Mortems, "What worked?" | Launching Jobs, Plotting Curves, Debugging |
| **Persistence** | High (Git History is readable) | Low (Cell outputs change constantly) |
| **Automation** | Updated via `Research Logger` skill | **Drivers the Automation** |

## 2. Recommendation Details

### A. The "Cockpit" Notebook
Instead of remembering CLI argumenst for `deploy_bare_metal.py`, `remote_cmd.py`, and `fetch_db.py`, we consolidate them into a **Control Plane Notebook**.

**Proposed Workflow in Notebook:**
1.  **Stage 1: Design**: Edit a YAML config cell (which saves to `configs/temp_run.yaml`).
2.  **Stage 2: Launch**: Run `!python scripts/deploy_bare_metal.py ...` directly from the cell.
3.  **Stage 3: Monitor**: A loop that queries `monitor_status.py` and updates a progress bar.
4.  **Stage 4: Analysis**:
    *   Auto-fetch `hpo.db` or `trade_log.csv`.
    *   Plot Cumulative Returns (VectorBT) *inline in the notebook*.
    *   Plot Loss Curves (WandB data).
5.  **Stage 5: Commit**: A button/cell that calls the `Research Logger` to append the final result to `randd_log.md`.

### B. The "Inventory" Structure
To organize the files generated by these experiments (checkpoints, logs), we recommend a strict folder hierarchy functionality, managed by the Notebook:

```text
experiments/
├── 01_Baseline_DQN/
│   ├── config.yaml
│   ├── deployment.log
│   └── report_card.md  <-- Auto-generated summary
├── 02_HPO_Alpha_Sweep/
└── ...
```

## 4. 3-Split Rolling Window Data Strategy

> [!IMPORTANT]
> The **Test Window is for Final Evaluation Only**. Never use it for model selection or hyperparameter tuning.

To prevent look-ahead bias and ensure robust model development, the pipeline uses a **3-Split Rolling Window** approach:

| Split | Purpose | Used In |
|---|---|---|
| **Train** | Model Learning | Gradient updates, policy optimization |
| **Validation** | Hyperparameter Selection | Optuna objective, early stopping |
| **Test (Trade)** | Final Evaluation | Out-of-sample performance, audit reports |

**Example (Monthly Folds):**
```
Fold 1: Train [Jan-Mar] → Validate [Apr] → Trade [May]
Fold 2: Train [Feb-Apr] → Validate [May] → Trade [Jun]
...
```

**Implementation:** `finrl_pro_ds/data/splitter.py` (`RollingWindowSplitter`)

## 6. Quality Assurance Protocols (Verification Tiers)

MANDATORY for all new experimental features or codebase refactors:

### Tier 1: Smoke Test (Sanity Check)
- **Goal**: Verify connectivity, environment setup, SSH access, and file uploads.
- **Config**: `--steps 100`, `--trials 1`.
- **Duration**: ~1 minute.
- **Outcome**: Confirms *connectivity*, NOT logic.

### Tier 2: Pilot Run (Logic Verification)
- **Goal**: Verify end-to-end pipeline logic, checkpointing, and memory stability.
- **Config**: `deepscalper_pilot_test.yaml` (100k steps).
- **Duration**: ~10-15 minutes.
- **Outcome**: REQUIRED pass before full production run.

### Tier 3: Production Run
- **Goal**: Model convergence and maximum performance.
- **Config**: `deepscalper_unified.yaml` (Full steps, full data).
- **Outcome**: Final Model Artifacts.
